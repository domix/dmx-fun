dmx-fun ships Jackson serializers and deserializers for all its types as two **optional**
modules, one per Jackson line. The core `fun` library has no runtime dependency on Jackson.

## Which module do I need?

Jackson 2 (`com.fasterxml.jackson.*`) and Jackson 3 (`tools.jackson.*`) are binary-incompatible
and both are maintained upstream. Pick the module that matches the Jackson your stack already
uses; the JSON produced is identical, so documents written by one line are read by the other.

| Your stack | Module | Base package | Spring Boot opt-out property |
|---|---|---|---|
| Spring Boot 4, Spring Framework 7, or Jackson 3 directly | `codes.domix:fun-jackson3` **(primary)** | `dmx.fun.jackson3` | `dmx.fun.jackson3.enabled` |
| Spring Boot 3, or Jackson 2 directly | `codes.domix:fun-jackson2` | `dmx.fun.jackson2` | `dmx.fun.jackson2.enabled` |

Both modules can sit on the same classpath and module path (`dmx.fun.jackson3` and
`dmx.fun.jackson2`), which matters for mixed Boot 3 / Boot 4 deployments. `fun-jackson3` is the
primary line: new features land there first. `fun-jackson2` receives bug fixes and version bumps
while Spring Boot 3 is in open-source support. The rule behind this split, its trigger and the
retirement policy are recorded in <a href={`${base}adr/adr-024-parallel-peer-major-lines`}>ADR-024</a>.

### Migrating from `fun-jackson` (0.2.x and earlier)

In 0.3.0 the Jackson 2 module was renamed so that every line carries its major version:

| | 0.2.x | 0.3.0+ |
|---|---|---|
| Artifact | `codes.domix:fun-jackson` | `codes.domix:fun-jackson2` |
| JPMS module / package | `dmx.fun.jackson` | `dmx.fun.jackson2` |
| Import | `dmx.fun.jackson.DmxFunModule` | `dmx.fun.jackson2.DmxFunModule` |
| Spring Boot opt-out property | `dmx.fun.jackson.enabled` | `dmx.fun.jackson2.enabled` |

Nothing else changes: the JSON shapes and the serializer behaviour are the same.

## Adding the dependency

line on your own classpath. Supported ranges: **3.0.x through 3.3.x** for `fun-jackson3` and
**2.14.x through 2.23.x** for `fun-jackson2` (see [version compatibility](#version-compatibility)).

## JSON shapes

| Type                 | Success / present | Failure / absent       |
|----------------------|-------------------|------------------------|
| `Option<T>`          | `v` (unwrapped)   | `null`                 |
| `Result<V, E>`       | `{"ok": v}`       | `{"err": e}`           |
| `Try<V>`             | `v` (unwrapped)   | `{"error": "msg"}` or `{"error": null}` |
| `Validated<E, A>`    | `{"valid": a}`    | `{"invalid": e}`       |
| `Either<L, R>`       | `{"right": v}`    | `{"left": v}`          |
| `Tuple2<A, B>`       | `[a, b]`          | —                      |
| `Tuple3<A, B, C>`    | `[a, b, c]`       | —                      |
| `Tuple4<A, B, C, D>` | `[a, b, c, d]`    | —                      |
| `NonEmptyList<T>`    | `[head, ...tail]` | —                      |
| `NonEmptySet<T>`     | `[head, ...rest]` | —                      |
| `NonEmptyMap<K, V>`  | `{k: v, ...}`     | —                      |

### Auto-configuration with `fun-spring-boot`

If you use `fun-spring-boot` (instead of wiring things manually), `DmxFunModule` is
registered as a Spring bean automatically whenever `jackson-databind` and the matching dmx-fun
module are on the classpath. Spring Boot's `JacksonAutoConfiguration` discovers all module beans
and applies them to the mapper — no `@Bean DmxFunModule` declaration required. There is one
auto-configuration per line; they are independent, so an application with both lines on the
classpath gets both modules, each registered with its own mapper.

<SpringBootAuto/>

The auto-configuration follows standard Spring Boot conventions:

| Condition | Behaviour |
|---|---|
| `tools.jackson.core:jackson-databind` **and** `fun-jackson3` on classpath | Jackson 3 `DmxFunModule` bean registered (`DmxFunJackson3AutoConfiguration`) |
| `com.fasterxml.jackson.core:jackson-databind` **and** `fun-jackson2` on classpath | Jackson 2 `DmxFunModule` bean registered (`DmxFunJackson2AutoConfiguration`) |
| User declares own `DmxFunModule` `@Bean` | That line's auto-configuration backs off (`@ConditionalOnMissingBean`) |
| `dmx.fun.jackson3.enabled=false` / `dmx.fun.jackson2.enabled=false` | That line's auto-configuration disabled entirely |

## Known limitations

### `Try.failure` loses the exception type

`Try.failure(ex)` serializes as `{"error": "msg"}` where `msg` is
`ex.getMessage()`. If the exception has no message, the field is written as
`{"error": null}` and a `RuntimeException` with a `null` message is
reconstructed on deserialization. In all cases only the message survives —
the original exception class and stack trace are not preserved.

**Workaround**: convert `Try<V>` to `Result<V, String>` via `toResult(Throwable::getMessage)`
before serializing if the exception type matters to consumers.

### `Try.success` with object values that have a single `"error"` string field

The deserializer detects a `Failure` by checking whether the JSON object has
exactly one field named `"error"` containing a string. If a success value is a
POJO that happens to serialize as `{"error": "some text"}` (one string field
named `"error"`), it will be misread as a `Failure` on deserialization.

**Workaround**: avoid using `Try<V>` for types whose JSON shape is
`{"error": "<string>"}`. Use `Result<V, E>` instead, which uses an explicit
`"ok"` / `"err"` envelope that cannot be confused with value content.

### Type parameters require `TypeReference`

Without a `TypeReference`, Jackson loses the generic type information at
deserialization time and returns raw `LinkedHashMap` / `ArrayList` instead of
the intended element types. Always use `TypeReference<Option<String>>()`,
`TypeReference<Result<Integer, String>>()`, etc.
