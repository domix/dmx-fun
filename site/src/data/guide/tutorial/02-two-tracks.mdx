Chapter 1 left `enroll` as a staircase: five `if`s, each with an early `return Result.err(...)`.
It is correct and it is tedious, and the tedium grows with every step you add. This chapter
rewrites the same method as a chain.

## Small steps first

Each check becomes a method that returns a `Result`. The methods do not know about each other:

<Steps/>

Each one answers a single question and hands back either the thing the next step needs or the
error that explains why it cannot. The `null` checks and the `try/catch` are still here; they
move out in chapters 3 and 4.

## Then the chain

<Enroll/>

Read it as two tracks. On the success track, each `flatMap` takes the value from the previous
step, runs the next step, and passes its value on. The moment a step returns an `Err`, the value
switches to the failure track and every remaining `flatMap` and `map` is skipped; the error
travels to the end untouched. Nobody writes `if (result.isErr()) return result;` between steps,
because that is exactly what `flatMap` does.

Three operations cover almost everything you will do with a `Result`:

| | Takes | Use it when |
|---|---|---|
| `map` | a function that cannot fail | the next step always works: saving the enrollment |
| `flatMap` | a function that returns a `Result` | the next step can fail: every lookup and check |
| `recoverWith` | a function from the error to a `Result` | you want to turn some failures back into successes |

## Choosing which failures are failures

The last line is a design decision, not plumbing. Enrolling a student who is already enrolled
used to be an error. For the caller it is noise: they asked for an enrollment and one exists.
`recoverWith` looks at the error and, for `AlreadyEnrolled` only, returns the existing enrollment
as a success. Every other error passes through unchanged. The operation is now idempotent, and
the gateway is never charged a second time because the pipeline never reached `charge`.

## What changed since chapter 1

- The five `if`/`return` pairs became five one-line methods and one chain.
- Failure propagation is implicit: the first `Err` wins and the rest is skipped.
- `AlreadyEnrolled` is no longer an error the caller sees; `recoverWith` absorbs it.

Still to fix: the `== null` checks inside the lookups, and the `try/catch` around the payment.
